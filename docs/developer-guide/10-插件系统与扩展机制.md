# 插件系统与扩展机制

## 1. 概述

Hermes Agent 提供三层扩展机制，从简单到强大：

| 机制 | 复杂度 | 说明 |
|---|---|---|
| **插件** | 简单 | Python 包，提供 hook 函数 |
| **MCP 工具** | 中等 | 外部 MCP 服务器提供的工具 |
| **ACP 集成** | 复杂 | IDE/编辑器的深度集成协议 |

插件现在不只是“hook 函数”。它也是多类后端的标准注入点：模型提供商、图像/视频生成、Web 搜索/抽取、云浏览器、平台 adapter、记忆 provider 和 context engine 都有各自的插件注册面。

## 2. 插件系统

### 2.1 插件结构

```
~/.hermes/plugins/             # 用户插件目录（默认 opt-in）
  ├── my-plugin/
  │   ├── plugin.yaml
  │   ├── __init__.py
  │   ├── SKILL.md (可选)
  │   └── requirements.txt (可选)
  └── another-plugin/
      └── __init__.py

plugins/                        # 内置官方插件
  ├── context_engine/           # 上下文引擎插件
  ├── disk-cleanup/             # 磁盘清理
  ├── google_meet/              # Google Meet 集成
  ├── image_gen/                # 图像生成后端
  ├── memory/                   # 外部记忆后端
  ├── model-providers/          # 推理 provider profile 插件
  ├── video_gen/                # 视频生成后端
  ├── web/                      # web_search / web_extract 后端
  ├── browser/                  # 云浏览器后端
  ├── platforms/irc/            # 网关平台插件参考实现
  ├── observability/            # 可观测性
  ├── spotify/                  # Spotify 控制
  └── strike-freedom-cockpit/   # 仪表盘
```

插件发现来源：

| 来源 | 路径/机制 | 加载规则 |
|---|---|---|
| Bundled | 仓库 `plugins/` 或 `HERMES_BUNDLED_PLUGINS` | `backend` 和 `platform` 自动加载 |
| User | `get_hermes_home()/plugins` | 通过 `plugins.enabled` 显式启用 |
| Project | 当前项目 `.hermes/plugins` | 需 `HERMES_ENABLE_PROJECT_PLUGINS`，再显式启用 |
| Pip | `hermes_agent.plugins` entry point | 显式启用 |

目录插件需要 `plugin.yaml` manifest 和带 `register(ctx)` 的 `__init__.py`。Manifest 的 `kind` 支持 `standalone`、`backend`、`exclusive`、`platform`。

`model-provider` 是特殊 kind：general plugin scanner 会识别但不导入，真正加载由 `providers/__init__.py` 的懒发现负责。这样可以避免同一个 `ProviderProfile` 被重复实例化，并允许用户插件以 last-writer-wins 覆盖内置 provider。


### 2.4 上下文引擎插件 (plugins/context_engine/)

允许用户为 Agent 提供自定义的提示词片段：

```python
def on_context_assembly(current_prompt):
    """在提示词组装时注入自定义内容"""
    return current_prompt + "\n[Custom rules from my plugin...]"
```

### 2.5 平台插件

网关平台也可以作为插件注册，不需要修改核心平台枚举或 adapter factory：

```python
def register(ctx):
    ctx.register_platform(
        name="irc",
        label="IRC",
        adapter_factory=lambda cfg: IRCAdapter(cfg),
        check_fn=check_requirements,
        validate_config=validate_config,
        is_connected=is_connected,
        required_env=["IRC_SERVER", "IRC_CHANNEL", "IRC_NICKNAME"],
        setup_fn=interactive_setup,
        allowed_users_env="IRC_ALLOWED_USERS",
        allow_all_env="IRC_ALLOW_ALL_USERS",
        cron_deliver_env_var="IRC_HOME_CHANNEL",
        standalone_sender_fn=send_without_gateway,
        env_enablement_fn=detect_env_enabled,
        max_message_length=450,
        platform_hint="You are chatting via IRC. Use plain text only.",
    )
```

注册信息进入 `gateway.platform_registry.platform_registry`。`Platform("irc")` 会通过动态 `_missing_()` 创建稳定的插件平台枚举成员，`toolsets.py` 会为 `hermes-irc` 自动生成核心工具集并合并插件工具。

平台插件如果要完整参与 cron 和脚本通知，需要补齐三个可选 hook：

- `env_enablement_fn`：让 `gateway status`、setup 和可用性检查在 adapter 实例化前就能从环境变量判断平台是否启用。
- `cron_deliver_env_var`：声明 cron/home-channel 的目标环境变量，避免改 `cron/scheduler.py`。
- `standalone_sender_fn`：让 `hermes send` 和独立 cron 进程在没有运行 gateway 的情况下也能调用平台 SDK 发消息。

内置参考可看 `plugins/platforms/{irc,teams,google_chat}/`。

## 3. MCP (Model Context Protocol)

### 3.1 架构

```
AIAgent
  │
  ├── ToolRegistry
  │     └── mcp_tool.py (MCP 客户端)
  │           ├── MCP Server 1 (filesystem)
  │           ├── MCP Server 2 (puppeteer)
  │           ├── MCP Server 3 (database)
  │           └── MCP Server N (custom)
  │
  └── 工具调用 → registry.dispatch() → MCP handler
```

### 3.2 功能

| 功能 | 说明 |
|---|---|
| **工具发现** | `tools/list` 请求获取服务器提供的工具列表 |
| **工具执行** | `tools/call` 请求调用具体工具 |
| **动态更新** | `notifications/tools/list_changed` 触发工具重新发现 |
| **多发器管理** | 并发连接多个 MCP 服务器，每个独立管理 |
| **OAuth 支持** | `tools/mcp_oauth.py` + `tools/mcp_oauth_manager.py` 管理授权 |

### 3.3 动态注册/注销

```python
# MCP 工具的热注册
for tool in mcp_server_tools:
    registry.register(
        name=f"mcp-{tool.name}",
        toolset=f"mcp-{server_name}",
        schema=tool.inputSchema,
        handler=create_mcp_handler(server_name, tool.name),
    )

# 服务器刷新时的热注销
for tool in old_tools:
    registry.deregister(tool.name)
```

### 3.4 配置

```yaml
# ~/.hermes/config.yaml
mcp:
  servers:
    filesystem:
      command: "npx"
      args: ["-y", "@modelcontextprotocol/server-filesystem", "/path/to/allowed"]
    puppeteer:
      command: "npx"
      args: ["-y", "@modelcontextprotocol/server-puppeteer"]
```

## 4. ACP (Agent Communication Protocol)

### 4.1 什么是 ACP

ACP 是 **代理-编辑器通信协议**（`agent-client-protocol`），允许 Hermes Agent 与 IDE/编辑器深度集成：

```
IDE (VS Code / JetBrains)
  │ ←── ACP Protocol ──→ │
  │                    Hermes ACP Server
  │                    (acp_adapter/server.py ~38K)
  │                         │
  │                    AIAgent 实例
```

### 4.2 ACP Server 功能

| 功能 | 说明 |
|---|---|
| **会话管理** | IDE 可以创建/切换/关闭 Agent 会话 |
| **文件变更推送** | Agent 的文件修改实时同步到编辑器 |
| **诊断信息** | 获取编译错误、Lint 警告等 |
| **选区操作** | 对编辑器选中的代码片段操作 |
| **权限审批** | IDE 可以管理危险命令审批和文件编辑审批 |
| **工具结果渲染** | `acp_adapter/tools.py` 把 Hermes 工具输出转成编辑器原生 tool card，并把结构化错误标成 failed |
| **认证** | `acp_adapter/auth.py` 提供安全认证 |

近期 ACP 的编辑审批不再只是“命令审批”的变体：`acp_adapter/edit_approval.py` 会在 `write_file` / `patch` 执行前生成 diff proposal。会话模式通过 `accept_edits` 等 mode 管理自动批准范围；敏感路径仍会回到 ask 流程。工具开始/完成事件由 `acp_adapter/events.py` 与 `acp_adapter/tools.py` 统一格式化，避免审批卡片和工具卡片重复展示同一个 diff。

### 4.3 ACP 注册中心 (acp_registry/)

定义 Agent 元数据和图标，使其能被 ACP 兼容的编辑器发现和连接。

```json
// acp_registry/agent.json
{
    "name": "Hermes Agent",
    "version": "0.11.0",
    "capabilities": ["terminal", "file_ops", "browser", ...]
}
```

## 5. 三种扩展方式的比较

| 维度 | 插件 | MCP | ACP |
|---|---|---|---|
| **目的** | 行为扩展（钩子） | 工具扩展（能力） | IDE 集成 |
| **开发语言** | Python | 任意 | 任意（通过 stdio/HTTP） |
| **安装** | 本地目录 | 配置文件指定命令 | 编辑器配置 |
| **隔离性** | 进程内（同 Python 进程） | 独立进程 | 独立进程 |
| **典型场景** | 自定义审批逻辑、日志钩子 | 数据库查询、API 调用 | IDE 内使用 Agent |

## 6. 其他扩展点

### 6.1 生成式媒体后端

图像和视频生成都已经走 provider 插件：

| 能力 | Provider ABC | 注册方法 | 配置键 | 工具 |
|---|---|---|---|---|
| 图像生成 | `agent/image_gen_provider.py::ImageGenProvider` | `ctx.register_image_gen_provider(...)` | `image_gen.provider` | `image_generate` |
| 视频生成 | `agent/video_gen_provider.py::VideoGenProvider` | `ctx.register_video_gen_provider(...)` | `video_gen.provider` | `video_generate` |

`video_generate` 是统一入口：有 `image_url` 时走 image-to-video，否则走 text-to-video。视频编辑/延展没有塞进这个统一 schema，后续需要时应作为独立工具设计。

### 6.2 记忆后端 (plugins/memory/)

外部记忆后端，支持：
- 内置文件系统（默认）
- Honcho（辩证用户建模）
- 自定义后端

### 6.3 可观测性 (plugins/observability/)

Agent 行为和性能的监控后端。

### 6.4 Web 与浏览器后端

`web_search` / `web_extract` / `web_crawl` 后端通过 `agent/web_search_provider.py::WebSearchProvider` 和 `ctx.register_web_search_provider(...)` 注册，配置键是 `web.search_backend`、`web.extract_backend` 或共享 fallback `web.backend`。

云浏览器通过 `agent/browser_provider.py::BrowserProvider` 和 `ctx.register_browser_provider(...)` 注册，配置键是 `browser.cloud_provider`。旧的 `tools/browser_providers/` 已删除，`tools/browser_tool.py` 现在从 `agent.browser_registry` 解析 Browserbase、Browser Use、Firecrawl 等 provider。
